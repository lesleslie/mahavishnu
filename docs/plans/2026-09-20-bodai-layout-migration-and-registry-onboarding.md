# Bodai layout migration + registry onboarding (cmux-mcp, flowscape)

## Context

The user noticed that **cmux-mcp** uses `src/`-layout (`src/cmux_mcp/`) while every other Bodai-managed repo uses flat layout (package directory at repo root with the package's underscored name). They asked for a quick cross-repo check, which revealed:

- **35/35 active repos in `BODAI_REPO_REGISTRY.md` are flat.** Convention is firm: `crackerjack/`, `mahavishnu/`, `akosha/`, every MCP server under `/Users/les/Projects/*-mcp/` — all flat. Verified via directory structure AND explicit `[tool.hatch.build.targets.wheel] packages = ["<name>"]` markers in `pyproject.toml`.
- **Two outliers:** cmux-mcp (`src/cmux_mcp/`) and flowscape (`src/flowscape/`, hybrid Swift + Python).
- **Neither was in the Bodai registry markdown.** `flowscape` IS in `settings/ecosystem.yaml` (lines 138-161) but missing from the generated markdown — confirmed drift via `regen_bodai_registry.py --check` returning `DRIFT`. cmux-mcp is missing from both.
- chat-bridge-mcp was suggested as a third outlier but is **already registered and already flat** — no action needed.

The user picked: **migrate both, register both, keep `cmux-mcp/scripts/README.md` as defense-in-depth.**

The user also asked whether mcp-common's MCP server template generates `src/`-layout. Investigation found: **no template in mcp-common**, but **`crackerjack/templates/`** has three pyproject templates (`minimal`, `library`, `full`) auto-selected by **`/crackerjack:init`**. Those templates are layout-agnostic — they don't specify `[tool.hatch.build.targets.wheel] packages = ...`. The src-layout in cmux-mcp came from upstream `hatch new --src`, not from any Bodai tool. A separate "Phase 2: prevent regression" item covers hardening `/crackerjack:init` against future src-layout drift.

**Outcome:** both repos conform to the Bodai flat-layout convention; both appear in the registry; crackerjack's path-resolving tooling (`_build_targets()`, `tc-refs`, hatch integration) works the same on them as on every other Bodai repo; the registry drift is resolved; the upstream template is hardened so future MCP servers won't accidentally land in src/-layout.

## Phase 3: prevent regression (prevention — addresses the user's mcp-common-template question)

**Investigation outcome:** the user assumed the template is in mcp-common. It is not. The actual templates live in `crackerjack/templates/` (three pyproject templates: `minimal`, `library`, `full`), auto-selected by `/crackerjack:init` (slash command at `/Users/les/Projects/crackerjack/commands/crackerjack-init.md`).

**Key finding:** the crackerjack templates are **layout-agnostic**. None of them specify `[tool.hatch.build.targets.wheel] packages = ...`. So they don't enforce either layout. The src-layout in cmux-mcp came from upstream `hatch new --src` (the default hatch template), not from any Bodai tool. Same for flowscape.

**Implication:** prevention is straightforward — make the layout explicit in `/crackerjack:init`'s docs and add a crackerjack lint that flags `packages = ["src/<pkg>"]`.

### Edit 3.1: crackerjack-init.md (document the convention)

`/Users/les/Projects/crackerjack/commands/crackerjack-init.md` — add a "Layout" section after the "What It Does" section that states:

> **Layout requirement:** Bodai convention is **flat layout**. The Python package directory must sit at the repo root with the package's underscored name (e.g., `cmux_mcp/`), NOT under `src/` (e.g., `src/cmux_mcp/`). The crackerjack templates use `<PACKAGE_NAME>` as a placeholder for the source directory; do not wrap that in a `src/` parent. If you accidentally ran `hatch new --src`, move the package to the repo root and update `pyproject.toml` to `packages = ["<PACKAGE_NAME>"]` before invoking `/crackerjack:init`.

### Edit 3.2: crackerjack/templates/README.md (annotate the convention)

`/Users/les/Projects/crackerjack/templates/README.md` — under "Usage", add a short note:

> All three templates assume **flat layout** (Bodai convention). The `<PACKAGE_NAME>` placeholder resolves to a top-level directory matching the package name. `src/<PACKAGE_NAME>/` is not a supported layout.

### Edit 3.3: add a crackerjack layout-convention lint (recommended but optional)

Add a `lints/src_layout.py` hook to crackerjack that scans `pyproject.toml` for `packages = ["src/<pkg>"]` and exits non-zero with a clear message:

```
ERROR: src-layout detected in <repo>/pyproject.toml
  Found: packages = ["src/<pkg>"]
  Expected: packages = ["<pkg>"]  (flat layout)
  See: /Users/les/Projects/crackerjack/commands/crackerjack-init.md (Layout requirement)
```

Wire this into `crackerjack run` (likely `fast_hooks` since the check is cheap). This is the durable enforcement mechanism.

**Decision:** include this in the plan now, but as a single commit after the migration commits. If implementation is more involved than expected, defer to a separate PR with a `crackerjack run` fast-hook integration test.
