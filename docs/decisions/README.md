| `2026-11-15-mcp-dispatch-liveness-heartbeat.md` | A long MCP dispatch stays alive by **reporting progress**, not by raising the timeout. Claude Code's MCP client has three separate timers: the **idle** timer (reset by progress notifications; aborts a call that produces neither a response nor progress) and the **wall clock** (never reset; defaults to `1e8` ms, ~28 h) and a startup timer. The idle timer is what kills healthy work — a pool dispatch sits in a worker for minutes with nothing to say, and the client aborts at the idle window with the work stranded. The per-server `.mcp.json` `timeout` is the **wrong lever**: it feeds both timers (`idle = min(max(env_idle, perServer), wall)`, `wall = perServer`), so setting one collapses idle and wall into the same value and makes progress reporting pointless. Rule: fix the idleness, never raise a timeout. The client attaches `_meta.progressToken` on every tool call (because it passes a no-op `onprogress` callback) and resets the idle clock on `notifications/progress`, so a server-side heartbeat is sufficient — the wall clock still ends a wedged call. Two load-bearing traps: `Context` must be imported at **runtime** (FastMCP resolves the injected parameter with `get_type_hints(fn)`; under `from __future__ import annotations` a TYPE_CHECKING-only import makes injection fail **silently**), and the heartbeat interval must resolve at **call time** so the module constant stays the single source of truth. | Active — implemented 2026-11-15 (`020798b5`); `mahavishnu_pool_route_execute` runs a 20-second heartbeat, the injected context is excluded from the tool schema (surface snapshot byte-identical), covered by `tests/unit/test_mcp/test_pool_route_progress.py` and `tests/integration/test_pool_route_progress_e2e.py`. **Deliberately not applied:** no per-server `timeout` in `.mcp.json`, and the global `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` is unchanged. |
| `2026-11-15-parallel-ensemble-review.md` | The stage-2 ensemble review dispatched its three reviewers one after another, and each dispatch is an I/O-bound MCP round trip to a worker pool — so a review cost the *sum* of the three reviewers rather than the slowest one. Making them concurrent raises the question the sequential version never had to answer: where do three reviewer sessions run? They all inherited the pool server's working directory, the shared main checkout, and on 2026-11-06 a reviewer in this same ensemble ran `git stash` there and disturbed another reviewer's work. The repo's rule for parallel agents on one repo is worktree isolation, and the dispatch was not using it. Rule: the three reviewers are dispatched concurrently (a `ThreadPoolExecutor`; each dispatch already owns its event loop, the synchronous dispatcher signature and the per-agent retry loop are unchanged, and the verdict list is still returned in dispatch order), and each is dispatched into its own worktree with `on_completion="discard"` — a reviewer must not merge anything back. The pool has to be able to honour the directory the task names: a task that names a working directory is routed only to a pool that reports it can, and that constraint travels with the queueing re-rank and the GPU category override — either of which can otherwise move the task onto a pool that ignores the directory, landing the reviewer in the shared checkout while the isolation check still passes (the worktree key says a worktree was *created*, not where the worker ran). The repository the isolated worktree is forked from is named in the prompt, because the server's own working directory is its own checkout and can therefore only ever name that repository - without it, every cross-repo merge asked for a worktree of a branch that does not exist there and died at stage 2. Naming a repository is a security boundary, so the server canonicalizes the resolved path and requires it to sit inside one of the operator's allowed repository roots. Isolation that cannot be provided is refused before the worker runs, not detected after it has already run in the shared checkout. The reviewer's reply has a budget - the pool captures the worker's terminal scrollback and keeps the newest bytes within a fixed bound - so the prompt states the budget and requires the verdict block to be the last thing the reviewer writes (see `2026-11-15-review-capture-window.md`). The retry-on-unreadable-verdict behaviour is untouched: a reviewer whose reply could not be read is still retried once, and a second failure still blocks. | Active — fixed 2026-11-15; covered by `tests/unit/core/test_merge_to_main.py`, `tests/unit/core/test_merge_to_main_gaps.py`, `tests/unit/core/test_merge_to_main_stash.py`, `tests/unit/pools/test_working_directory_routing.py`, `tests/unit/test_merge_review_isolation.py`, `tests/unit/test_mcp/test_pool_tools_worktree.py` and `tests/integration/test_pool_worktree_isolation.py`. One behavioural difference: if a dispatcher raises outright, the concurrent version waits for the other two reviews (a running thread cannot be cancelled), where the sequential version aborted at once — in practice `dispatch_review` catches every transport failure and returns a fail-loud reply, so the raise path is a corner case. |

| `2026-11-15-review-capture-window.md` | The stage-2 review does not receive the reviewer's answer directly: it polls the worker's tmux pane until the CLI's completion marker appears and parses the verdict out of **what the capture returned**, so the capture is load-bearing for the merge — a truncated reply carries no readable verdict, and an unreadable verdict is a fail-loud `block`. The capture was reading only the visible pane (`since_offset=0` → `tmux capture-pane -S -0`), and the pane is 24 rows of 80 columns, so a reply past about 1,920 characters wrapped off the top of the screen and arrived with its opening cut off. Measured on a real pane: 1,744 bytes of a reply whose verdict block had scrolled away, and the verdict did not parse — a review that ran perfectly well gated the merge as a block, with nothing in the verdict to say the reply had been cut. The shared `capture_pane` also truncated by keeping the **oldest** bytes (`encoded[:max_bytes]`), which is backwards for a capture of a *live* pane — the answer is written last — and that became load-bearing the moment the capture was widened: a review's scrollback crosses 64 KB at roughly 600 tool calls (measured 118 KB from 600 events), and the head-truncation would then delete the result line outright, replacing "the reply is cut" with "the reply is gone". The prompt compounded it by stating a budget that was not real ("about three minutes", cut off "by the transport the reply travels over"). The three minutes was never measured; what *is* measured is that a call held open through this client's MCP transport for 420 s came back with its payload intact, and reviews have run to 855 s and 1168 s and delivered a verdict — while `REVIEW_DISPATCH_TIMEOUT`'s own comment asserted the opposite ("the budget the reviewer actually has is minutes, not an hour"), so the prompt and the constant it reads contradicted each other, which is how a reviewer caught it. Neither now claims a mechanism nobody confirmed: the client's httpx read timeout is 300 s on a quiet stream and the server's dispatch heartbeat *is* a no-op for a client that sends no progress token (this one does not), so those two facts do not fit together neatly — a reason to state the measurement rather than a mechanism. A budget stated three times too short makes a reviewer rush, and a reviewer that rushes writes a long reply to compensate, which is what pushes it past the capture bound; the prompt also quoted a 600-character note length while the sanitizer caps a note at 500. Rule: a capture of a live pane keeps the **newest** bytes; the terminal adapter reads the scrollback (`CAPTURE_SCROLLBACK_LINES`, tmux's default history limit) and honours the `lines` argument the adapter contract already offers and the adapter previously ignored (the bound is applied in the adapter, because tmux's `-S -N` returns N scrollback rows *plus* the visible pane); the prompt states the dispatch's ceiling — read from the constant so the number cannot drift — tells the reviewer not to plan on spending it, and quotes the note length from `MAX_NOTE_LENGTH`, the cap that is actually enforced; the verdict block stays the last thing the reviewer writes, because the capture is bounded at the end; the reply is taken from the **last** `"result"` event in the capture, because a session that ran more than one turn carries more than one; and the prompt's reply budget (`REVIEW_REPLY_BUDGET_CHARS`, 1,500) deliberately stays **smaller** than what the capture can hold — the budget is the advice that keeps a review inside its budget, and it has to fit a capture smaller than this repo's (the visible pane is 24 rows of 80 columns, and a reply past about that used to arrive with its opening cut off) — without advertising the extra room, which would invite a reviewer to overrun it in the window between the change landing and the server picking it up. | Active — fixed 2026-11-15; covered by `tests/unit/terminal/test_tmux_adapter_capture.py`, `tests/unit/workers/contract/test_tmux_adapter.py`, `tests/unit/test_merge_review_dispatcher.py` and `tests/integration/test_review_capture_window.py` (a real tmux pane whose reply overflows the visible screen, failing against the old capture with `malformed: <verdict> block not found in agent response`). |
